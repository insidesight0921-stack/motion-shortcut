# 기술 결정 기록

형식: **결정 / 대안 / 선택 이유 / 되돌릴 조건**. 시행착오(안 되던 것과 해결법)도 지우지 않고 아래 "시행착오" 절에 남긴다.

## D-001 패키지 버전 고정

- **결정**: react 18.3.1, vite 7.3.6, @vitejs/plugin-react 5.2.0, vitest 4.1.11, typescript ~5.9, zustand 5.0.15, @mediapipe/tasks-vision 1.0.1
- **대안**: react 19.2, vite 8.2(Rolldown), vitest 5.0, typescript 7.0
- **선택 이유**: 기획에서 React 18 확정. Vite 8과 vitest 5는 2026-08~09에 나온 새 메이저라 해커톤 기간에 생태계 이슈를 밟을 위험이 있음. plugin-react 6.x는 peer가 `vite ^8`이라 5.2.0을 사용(peer `^7` 확인). TypeScript 7은 네이티브 포트 신버전이라 제외.
- **되돌릴 조건**: 해커톤 이후 안정화되면 메이저 업데이트. React 19는 기획 결정 변경 시.

## D-002 @mediapipe/tasks-vision 1.0.1과 WASM CDN 버전 고정

- **결정**: 패키지 1.0.1을 쓰고, WASM은 `https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@1.0.1/wasm`으로 **버전을 명시**해 로드. 모델은 Google Storage의 `hand_landmarker.task` float16 v1.
- **대안**: (a) README 예시처럼 버전 미지정 CDN 경로, (b) 0.10.x 마지막 버전, (c) 처음부터 로컬 번들
- **선택 이유**: 1.0.1은 2026-07-31 공개된 정식 릴리스(레지스트리에 보이는 `1.0.1-rc.2026MMDD`는 nightly 태그이며 별개). `vision.d.ts`를 직접 읽어 `FilesetResolver.forVisionTasks`, `HandLandmarker.createFromOptions`, `detectForVideo`, `HandLandmarkerResult.handedness` 시그니처를 확인했고 0.10.x와 동일함. JS 번들과 WASM 버전이 어긋나면 로드 실패가 나므로 CDN 경로에도 같은 버전을 박음. WASM 6개 파일이 npm 패키지에 포함돼 있어서 나중에 `public/`으로 복사하면 로컬 번들 전환이 쉬움(`vision/assets.ts` 상수만 바꾸면 됨).
- **되돌릴 조건**: GPU 델리게이트 초기화 실패 등 런타임 문제가 나오면 먼저 `delegate: 'CPU'`로 전환, 그래도 안 되면 0.10 마지막 버전으로 하향. 오프라인 데모가 필요하면 로컬 번들로 전환.

## D-003 좌표계: 사용자 시점 통일, 거울 변환은 한 곳에서만

- **결정**: `vision/mirror.ts`의 `toUserFrame()`에서 `x → 1 - x`를 한 번 적용. 그 이후 오버레이·판정·테스트는 모두 "사용자 오른쪽 = x 증가 = 화면 오른쪽". 미리보기 `<video>`는 CSS `scaleX(-1)`로 거울 표시. 오버레이 캔버스는 뒤집지 않고 변환된 좌표를 그린다.
- **대안**: (a) 캔버스도 CSS로 뒤집고 원본 좌표를 그림, (b) 판정 함수 안에서 부호만 뒤집음
- **선택 이유**: 반전이 두 군데 이상 있으면 언젠가 두 번 적용되어 좌우가 바뀐다. 변환 지점을 하나로 두고 유닛 테스트에 "x 증가 궤적 → swipe_right"를 고정하는 것이 가장 안전.
- **되돌릴 조건**: 후면 카메라(거울 아님)를 지원하게 되면 `mirror` 플래그를 설정으로 뺀다.

## D-004 엄지 펼침 판정: x축 규칙 대신 손 방향 무관 규칙

- **결정**: 엄지 끝(4)이 새끼 MCP(17)로부터 엄지 IP(3)보다 `thumbExtendMargin`만큼 더 멀면 펼침으로 본다.
- **대안**: 기획 초안의 "엄지는 x축 기준 별도 처리" (엄지 끝 x가 엄지 IP x보다 바깥쪽이면 펼침)
- **선택 이유(비교)**:
  | 항목 | x축 규칙 | 거리 규칙(채택) |
  |---|---|---|
  | 왼손/오른손 | 부호가 뒤집혀 handedness가 필요 | 무관 |
  | 거울 변환 | 변환 여부에 따라 부호 재검토 필요 | 무관 |
  | 손이 기울어짐(회전) | 손이 눕거나 돌아가면 x축 의미가 사라짐 | 손 내부 거리라 회전에 강함 |
  | 직관성 | 단순 | 조금 덜 직관적, 문서 필요 |
  HandLandmarker의 handedness는 "입력이 거울 이미지라는 가정"으로 계산되어 신뢰하기 애매하고, 주먹 판정은 엄지를 제외하므로 이 규칙은 손바닥 판정에만 영향. 실기 튜닝 부담을 줄이는 쪽을 택함.
- **되돌릴 조건**: 실기에서 엄지를 접은 채 나머지를 편 손이 손바닥으로 잡히는 오탐이 잦으면 두 규칙을 AND로 결합하거나 마진을 올린다.

## D-005 스와이프 거리 단위는 손 크기 배수

- **결정**: 스와이프 이동량을 화면 비율이 아니라 "손목–중지MCP 거리(손 크기)"의 배수로 판정한다.
- **대안**: 화면 폭 대비 비율(예: 0.25)
- **선택 이유**: 카메라와의 거리가 달라지면 같은 동작도 화면상 이동량이 달라진다. 손 크기로 나누면 거리에 덜 민감.
- **되돌릴 조건**: 손이 화면 가장자리에 걸려 손 크기 추정이 흔들리면 화면 비율과 혼합.

## D-006 동적 제스처는 정규화 전 좌표로 판정

- **결정**: `TrajectoryBuffer`에는 사용자 시점 프레임의 원본(0~1) 좌표와 손 크기를 저장하고, 스와이프·원은 이 좌표로 판정한다. 정규화 좌표는 정적 포즈에만 쓴다.
- **선택 이유**: 손목 기준 정규화는 평행이동을 제거하므로 손 전체가 움직이는 스와이프는 정규화 좌표에서 보이지 않는다(시행착오 예방 차원에서 기록).

## D-007 활성화 단축키 Ctrl+Shift+M

- **결정**: 모든 플랫폼에서 `Ctrl+Shift+M` (macOS도 Cmd가 아닌 Ctrl).
- **대안**: Cmd+Shift+M, Space
- **선택 이유**: Cmd+Shift+M은 Chrome 프로필 메뉴에 이미 묶여 있음. Space는 YouTube iframe이나 버튼 포커스와 충돌.
- **되돌릴 조건**: 팀원 환경에서 충돌 보고 시 `ui/shortcuts.ts` 상수 변경.

## D-008 상태 머신 세부 규칙

- **결정**: `executing → cooldown` 전이에서 `TrajectoryBuffer.clear()`를 호출한다. 정적 제스처는 실행 후 포즈를 한 번 놓아야(release) 재무장된다. 원 판정의 누적 회전각은 **부호 있는 합**으로 계산해 왕복(좌우로 흔들기)이 원으로 잡히지 않게 한다. ~~쿨다운 중 같은 제스처 후보가 계속 보이면 쿨다운 만료 시각을 계속 뒤로 미룬다.~~ → **T-003으로 제거** (2026-09-08).
- **선택 이유**: 실행 직후 버퍼에 남은 궤적이 다음 틱에서 같은 제스처로 재검출되는 것을 막는다. 손바닥을 계속 들고 있는 동안 재생/일시정지가 반복되는 것은 release 규칙이 막는다. 부호 없는 합은 지그재그도 300°를 넘긴다.
- **되돌릴 조건**: 없음(테스트로 고정).

## D-009 동적 제스처 점수와 임계값의 역할 분리

- **결정**: 스와이프·원은 `config`의 하드 조건(거리, 수직 편차, 직진성, 회전각, 반지름)을 **모두 통과해야만** 후보가 되고, 점수는 `0.5 + 0.5 × 품질`(통과 시 최소 0.5)로 계산해 별도 하한 `minDynamicScore`(0.5)와 비교한다.
- **대안**: 정적 포즈처럼 점수 하나에 모든 조건을 녹여 `minPoseScore`로 거르기
- **선택 이유**: 튜닝은 카메라 앞에서 사람이 슬라이더로 한다. "swipeMinDistance를 2.0으로 두었는데 실제로는 2.4를 움직여야 된다"처럼 점수 계산이 임계값의 의미를 바꾸면 튜닝이 불가능해진다. 하드 조건은 문서 값 그대로 동작하고, 점수는 "더 깨끗한 동작만 받고 싶을 때" 올리는 별도 손잡이로 남긴다.
- **되돌릴 조건**: 실기에서 하드 조건만으로 오탐이 잡히지 않아 연속 점수가 필요해지면 통합.

## D-010 원 vs 스와이프 구분: 회전 진행 보류 + 포인팅 손 모양 규칙

- **결정**: `detectDynamic`은 (1) 완성된 원, (2) 회전이 150° 이상 진행 중이면 스와이프 보류, (3) 스와이프 순서로 판정하고, 스와이프는 창 안 프레임의 절반 이상이 "검지만 편 손"이면 거부한다.
- **대안**: (a) 회전각 보류만, (b) 스와이프 수직 편차 상한을 0.2 이하로 조이기, (c) 원 최소 반지름을 키워 원을 작게만 그리게 하기
- **선택 이유**: 테스트로 확인한 사실 — 반지름 1.5 손 크기의 원을 1.8초에 그리면 첫 84°에서 이미 현 길이가 2.0 손 크기를 넘고 수직 편차는 0.19라 스와이프 조건을 모두 통과한다. 이때 회전 진행은 84°로 어떤 보류 각도로도 못 막는다(90°로 내리면 직선 스와이프의 ±180° 점프와 충돌). (b)는 사람의 자연스러운 곡선 스와이프를 죽인다. 기획서가 "검지로 원 그리기"라 했으므로 손 모양이 가장 자연스러운 구분자다.
- **되돌릴 조건**: 실기에서 원 그릴 때 다른 손가락이 접히지 않는 사용자가 많으면 `swipeMaxPointingFraction`을 1로 올려 규칙을 끄고 (c)로 전환.
- **알려진 한계**: 펼친 손으로 큰 원을 그리면 첫 호가 스와이프로 잡힐 수 있다. 테스트 파일에 회귀 감시용으로 기록.

## D-011 효과음은 WebAudio 오실레이터, 에셋 파일 없음

- **결정**: `ui/sound.ts`에서 `OscillatorNode`로 짧은 비프를 합성한다. 첫 클릭·키 입력에서 `AudioContext`를 깨운다.
- **대안**: mp3/wav 파일 + `<audio>`
- **선택 이유**: 저작권·용량·로딩 걱정이 없고, 실행/켜짐/꺼짐/타이머 네 가지를 음높이로 구분하기에 충분하다. 브라우저 자동재생 정책은 어느 쪽이든 첫 사용자 입력이 필요하다.
- **되돌릴 조건**: 디자이너가 사운드를 주면 교체. 인터페이스(`playSound(kind)`)는 그대로.

## D-012 개발 패널의 임계값은 메모리에만, 새로고침하면 기본값

- **결정**: 슬라이더 값은 zustand 스토어에만 있고 localStorage에 저장하지 않는다. "변경값 복사"로 JSON을 받아 `config.ts`에 손으로 반영한다.
- **대안**: localStorage 자동 저장
- **선택 이유**: 2인 협업에서 "내 브라우저에만 남은 값" 때문에 서로 다른 동작을 보는 상황을 막는다. 튜닝 결과는 코드와 문서에 남아야 한다는 요구사항과도 맞다.
- **되돌릴 조건**: 튜닝 세션이 길어져 새로고침마다 다시 맞추는 게 고통스러우면 "저장" 버튼을 명시적으로 추가(자동 저장은 하지 않음).

## D-013 로그는 스토어 + 콘솔 이중 기록, 200건 상한

- **결정**: `store/logStore`가 한 줄 형식(`시각 | 제스처 | 명령 | 결과 | 사유`)으로 만들어 화면 표와 `console.log('[motion] …')`에 동시에 쓴다. 최근 200건만 유지.
- **선택 이유**: 화면은 보기 편하고, 콘솔은 페이지가 멈춰도 남는다. 같은 문자열을 쓰므로 어느 쪽을 복사해도 동일하다. 200건은 30fps에서 무시 로그가 프레임마다 쌓이지 않도록 에피소드당 1회로 줄였기 때문에 충분하다.

  | 그림자 | 글로우·`0 6px 24px`·`0 4px 16px` → elevation 0/2/3, 다크는 없음 | §6 |

## D-015 요리 모드 제거, 범용 명령 + 사용자 매핑으로 전환 (2026-09-09, feat/generic-commands)

- **결정**: 제스처 5개는 그대로 두고(인식 파라미터 T-003~T-009 유지), 명령 계층과 UI를 "범용 명령 카탈로그 + 사용자가 편집하는 매핑"으로 바꾼다. 요리 모드 코드는 주석 처리가 아니라 삭제.
- **이유**: 특정 상황(요리)에 묶인 하드코딩 위에서는 디벨롭 방향을 정하기 어렵다. 어떤 상황에도 붙일 수 있는 기본형(제스처 ↔ 범용 명령)을 먼저 확보하고 그 위에서 방향을 고른다.
- **삭제 목록**: `src/modes/cooking/*` 7개(CookingMode, RecipeSteps, recipe, commands, mapping, Timer·YouTubePlayer는 이동 후 삭제), `src/store/cookingStore.ts`와 테스트, `src/ui/MappingTable.tsx`(읽기 전용 표), "요리 모드 · 1차 초안" 문구, 레시피 CSS.
- **새 구조**: `commands/`(types·catalog·registry·keyPress), `mapping/`(types·defaults·storage), `store/mappingStore`·`store/targetStore`(cookingStore를 범용화: 플레이어 핸들에 seekTo/getCurrentTime 추가, 타이머 길이 파라미터화, 마지막 키), `targets/youtube`·`targets/timer`(이동), `ui/MappingEditor`·`KeyCaptureInput`·`LastKeyIndicator`.
- **명령 카탈로그**: `media.playPause`, `media.seekForward(초)`, `media.seekBackward(초)`, `timer.toggle(분)`, `key.press(키 조합)`, `none`, `system.toggleEnabled`(주먹 전용, 드롭다운 비노출). 기본 매핑: 손바닥→재생/일시정지, 오른쪽→+10초, 왼쪽→−10초, 원→3분 타이머, 주먹→활성화(고정).
- **결정 1 — 주먹 토글은 엔진이 수행**: `useGestureEngine`이 fist 실행 시 `enabled`를 직접 뒤집는다. 카탈로그의 `system.toggleEnabled.run()`은 상태를 바꾸지 않고 메시지만 돌려준다. 매핑·명령 계층이 깨져도 잠금 해제 경로는 살아 있어야 한다. 저장소는 주먹 항목을 어떤 입력이든 고정값으로 덮어쓴다(테스트로 고정).
- **결정 2 — 스토어 범위**: `gestureStore`는 변경 없음. `cookingStore` → `targetStore` 범용화, `mappingStore` 신설, `logStore`의 결과 종류를 `executed / failed / ignored`로 정리(보완 2).
- **보완 1 — 키 캡처 안전장치**: `KeyCaptureInput`은 `isTrusted=false` 이벤트를 무시한다(우리 `key.press`가 캡처 입력에 되먹임되지 않음). 캡처 중에는 `mappingStore.capturing=true`이고 `runMapping(..., { paused })`이 모든 매핑 실행을 `ignored: 키 캡처 중`으로 돌린다. 주먹 토글은 엔진 담당이라 캡처 중에도 동작한다.
- **보완 3 — 합성 키 대상**: `dispatchKeyCombo` 기본 대상은 `document.activeElement ?? document.body`이되, activeElement가 `[data-mapping-editor]` 안이면 body. 방금 편집한 드롭다운이나 캡처 입력이 자기 자신에게 키를 받는 사고를 막는다. `resolveKeyTarget`으로 분리해 DOM 없이 테스트.
- **합성 KeyboardEvent의 `isTrusted` 한계와 다음 방향**: 스크립트가 만든 KeyboardEvent는 `isTrusted=false`다. 브라우저는 이 이벤트로 기본 동작(스크롤, 포커스 이동, 폼 제출)을 하지 않고, YouTube iframe 같은 다른 문서로 넘기지도 않는다. 즉 `key.press`는 **우리 페이지 안의 JS 리스너**에만 동작한다. 화면의 "마지막으로 받은 키" 카드가 그 사실을 보여 준다. 이 한계가 다음 단계의 출발점이다: 다른 웹앱을 제어하려면 (a) 대상 앱이 우리 SDK(`postMessage` 또는 스크립트)를 넣어 명령을 받거나, (b) 브라우저 확장 프로그램이 `chrome.debugger`/`Input.dispatchKeyEvent`로 신뢰된 입력을 만들어야 한다. 둘 다 이번 범위 밖이며 `Mode`/프리셋과 함께 만들지 않는다.
- **대안**: (a) 요리 모드를 남기고 "모드 전환"을 추가 — 기본형이 없는 채 모드만 늘어난다. (b) 매핑을 코드 상수로만 두기 — 사용자가 바꿔 보며 디벨롭 방향을 찾는 목적에 맞지 않는다.
- **되돌릴 조건**: 프리셋이 필요해지면 `mapping/presets/`를 추가한다(저장 형식에 `version`을 둔 이유). 사용자 정의 제스처·확장 프로그램·다른 탭 제어는 별도 결정.

## D-016 모드 시스템 도입 + 음성 전환 + 대기 모드 (2026-09-09, feat/mode-system)

- **결정**: 모드 = 매핑 + (나중에) 사용자 정의 제스처 세트 + 데모 대상 의 묶음. `media`·`reading`·`presentation`·`meeting` 4개와 시스템 모드 `standby`. 이번엔 뼈대만: media 만 동작하고 나머지는 빈 프리셋(전부 `none`, 주먹 고정). 전환 경로는 음성·화면 세그먼트·키보드(`Ctrl+Shift+1~4`, 대기 `Ctrl+Shift+0`)가 항상 공존한다. `gesture/`는 변경 없음(102개 테스트 불변).
- **음성은 전환에만 쓰는 이유**: 전환은 드물고 실패해도 다른 두 경로가 있어 시끄럽거나 조용한 환경의 제약이 작다. 명령은 빈도가 높고 지연·오인식에 민감해 제스처가 맡는다. 음성으로 명령까지 실행하면 "듣고 있는 마이크"가 상시 권한이 되어 사생활 부담도 커진다. `voice/keywords.ts`는 의도를 `switch:<mode>`, `standby`, `wake` 셋으로만 해석한다.
- **대기 모드가 제스처로 안 풀리는 이유**: 대기는 "카메라는 켜져 있지만 아무것도 실행하지 않는다"는 약속이다. 주먹(활성화 토글)으로 풀리면 대기 중 주먹을 쥐는 순간 약속이 깨진다. 그래서 `gestureGate`는 대기 중 주먹을 포함한 모든 실행을 막고, 해제는 `WAKE_SOURCES = voice/ui/key` 만 허용한다. 우선순위: 대기 > 활성화 off > 활성화 on.
- **모드 전환 쿨다운을 UI 층에 둔 이유**: 상태 머신의 쿨다운은 `enabled`만 알고 모드를 모르며 `gesture/`는 수정하지 않기로 했다. 대신 `modeStore.cooldownUntil`(1.5초)을 `useGestureEngine`이 실행 직전에 검사하고, 전환 시 공개 API `GesturePipeline.reset()`으로 궤적·유지 상태를 비운다. 전환 직전에 하던 동작이 새 모드에서 실행되는 것을 막는다.
- **키워드 매칭(보완 1)**: "모드"가 들어간 별칭은 정규화(공백·문장부호 제거) 후 **포함** 매칭. 한국어 발화는 "발표 모드로 바꿔줘"처럼 조사·서술어가 붙는 것이 기본형이라 완전 일치는 첫 실기에서 전부 실패한다. 단독 단어("발표")는 완전 일치만, 그리고 대기 중이 아닐 때만. 긴 별칭을 먼저 검사해 "미디어 모드"가 "미디어"에 잡히지 않게 한다. 매칭 실패는 로그에 `음성 | 무시 | 인식됨 · 의도 없음 · "<문장>"`으로 남겨 별칭을 늘릴 근거로 쓴다.
- **TTS 되먹임 방지**: 전환 확인음 "발표 모드"를 인식기가 다시 들으면 같은 전환이 반복될 수 있다. `useVoice`는 발화 동안 `recognizer.pause()`(abort, 재시작 억제) 하고 `onend`에서 `resume()`한다. ko-KR 음성이 없으면 발화를 건너뛰고 배지 변경만 한다(`voice.ttsAvailable`, 보완 2). 실기에서만 검증 가능.
- **Web Speech API의 온라인 의존**: Chrome 계열의 `SpeechRecognition`은 음성을 Google 서버로 보내 인식한다. 오프라인이면 `network` 오류로 3회 재시작 후 `error` 상태가 되고, UI·README에 그 사실을 적었다. Firefox 미지원, Safari는 `webkitSpeechRecognition`이 있으나 `continuous`가 불안정. 마이크 권한은 사용자가 "음성 켜기"를 눌렀을 때만 요청하고, 거부되면 버튼 대신 "주소창 자물쇠 → 마이크 허용 후 새로고침" 안내를 보여 준다(보완 3). TypeScript `lib.dom`에는 `SpeechRecognition` 본체 타입이 없어 `voice/speech.d.ts`에 최소 선언을 두었다.
- **마이그레이션**: 저장 키 `motion-shortcut.mapping.v2` = `{ version: 2, byMode }`. v2 가 없으면 v1(`…mapping.v1`)을 읽어 `media` 로 승격하고 나머지 모드는 카탈로그 기본값, 결과를 v2 로 저장한다. v1 은 지우지 않는다. 부분 누락·손상은 모드·항목 단위로 기본값 폴백, 주먹은 모든 모드에서 고정. D-015에서 `version` 필드를 남겨 둔 것이 여기서 쓰였다.
- **대안**: (a) 모드 없이 매핑 프리셋만 — "대상"과 "사용자 정의 제스처"를 묶을 자리가 없다. (b) 음성으로 명령까지 — 위 이유로 제외. (c) 대기 해제에 주먹 허용 — 대기의 의미가 사라진다.
- **되돌릴 조건**: 읽기·발표·회의 모드의 실제 대상은 다음 단계에서 `targets/`에 추가하고 `ModeDef.targets`만 채운다. 사용자 정의 제스처는 `ModeDef.customGestures` 자리에 붙인다. 별칭 사전은 실기 로그의 "의도 없음" 문장을 보고 늘린다.

## D-017 Flickey 전환: 발표자용 모션 프레젠테이션 인터페이스로 (2026-09-11, feat/flickey-1-core)

- **결정**: 제품을 Flickey(`docs/PRODUCT.md`)로 확정하고 기획서 §25 순서(1차 발표 제어 기반 → 2차 모드 → 3차 자료 → 4차 리허설 → 5차 개인화)로 단계 전환한다. 한 손 인식 엔진(`gesture/`, 테스트 102개)은 손대지 않고 양손은 `gesture/twoHands.ts`·`modeGesture.ts`를 **추가**한다. 음성(`voice/`)은 코드 보존·기본 OFF·설정 하단 실험 기능. YouTube·타이머·읽기 대상은 삭제.
- **아키텍처 경계**: 웹앱(이 레포: 카메라·인식·프로필·리허설·대기 화면·로그) + 로컬 에이전트(팀원, 별도 코드: OS 키·커서·레이저 창·자료 실행·미니 패널). 사이는 `ws://127.0.0.1:41777` JSON. 이 레포는 **프로토콜 명세(`docs/AGENT-PROTOCOL.md`)와 모의 에이전트**까지만 만든다. 에이전트가 없으면 페이지 안 폴백(합성 키·페이지 안 레이저)으로 단독 데모.
- **프로토콜에 삭제·이동·종료 메시지를 두지 않는 이유**: §16 높은 위험 명령은 실수 한 번이 발표를 끝낸다. 메시지 자체가 없으면 웹앱 버그로도 실행될 수 없다. MVP의 높은 위험 명령은 `slide.return`(Esc) 하나이고 이것도 `key` 메시지다. `open`은 웹앱·에이전트 **이중 화이트리스트**.
- **모션 OFF와 standby를 하나로 합친 이유**: 0단계 초안은 "모션 OFF(발표 세션 전역 스위치) > standby(모드) > 활성화 off > 실행"의 4단이었다. 그런데 standby의 정의(모든 제스처 무시, 한 손으로 해제 불가, D-016)가 기획서 §19 "모션 기본값 OFF + 복잡한 모션으로 ON/OFF"와 같고, §12 표시도 `MOTION OFF` 하나뿐이다. 개념이 둘이면 사용자에게 "모션은 켜졌는데 대기 모드"라는 설명 불가능한 상태가 생긴다. 그래서 **standby = MOTION OFF** 로 합친다. 양손 X 유지 = standby 토글, 발표 세션 시작 시 기본 standby, UI 표시명 `MOTION OFF`. 우선순위 체인은 `standby > 활성화 off(settings.motionToggle === 'fist'일 때만 존재) > 실행`으로 2~3단. 기존 `modeStore.gestureGate`·`WAKE_SOURCES`는 그대로 쓰고 `SwitchSource`에 `'gesture'`(양손 전환)를 추가한다. 양손 검지 교차 전환으로는 standby 해제를 허용하고 한 손 제스처로는 불가(§13 "지정한 복합 포즈 유지").
- **디자인 두 체계**: 발표 전 화면은 `docs/DESIGN.md`, 발표 중 오버레이는 `docs/DESIGN-OVERLAY.md`(검정·건메탈·백청색 발광·암적색·1초 소멸). DESIGN.md의 글로우 금지는 오버레이 범위에서 명시적 예외이며 사유는 그 문서 §2에 있다. 코드 경계는 `src/ui/overlay/` + `--ov-*` 토큰 + `ov-` 접두사.
- **프로필 모델과 저장 v3**: `Profile { id, name, program, mappingByMode(slide/cursor/laser/asset), assets[], rehearsal?(통계만), gestureOverrides?, settings }`, 키 `motion-shortcut.profiles.v3`. v2 `byMode` → v3: `presentation` → `slide`, `media`의 `key.press` 항목만 `slide`에 병합(겹치면 presentation 우선), 사라진 명령(`media.*`, `timer.toggle`)은 `none`, 나머지 모드는 기본값. v2·v1은 지우지 않는다.
- **모드 전환 방향**: 검지 교차 유지 → ↓ 슬라이드, ← 커서, → 레이저, ↑ 자료(기획서 §12에 자료 방향이 없어 제안값). `selectMinDistance`는 방향별 config(`selectMinDistanceByDirection`, 기본 동일값)로 분리해 실기 후 조정.
- **handedness**: MediaPipe는 입력이 거울 이미지라고 가정하고 Left/Right를 매긴다. 우리는 원본 프레임을 넣으므로 라벨이 사용자 기준과 반대일 가능성이 크다. `vision/handedness.ts` 한 곳에서만 뒤집고(D-003 원칙) 1차 실기 항목 1번으로 확인한다.
- **대안**: (a) 기존 모드 4개 위에 발표 모드만 추가 — 제품 정체성과 어긋나고 삭제 대상 코드가 남는다. (b) 에이전트 코드를 이 레포에 함께 — 팀 분담과 네이티브 빌드 파이프라인이 섞인다. (c) 양손을 기존 파이프라인 안에 넣기 — 102개 테스트와 튜닝값을 흔든다.
- **되돌릴 조건**: 에이전트가 기한 안에 나오지 않으면 페이지 안 폴백만으로 데모한다(그래서 폴백을 1차에 넣는다). 검지 교차 전환이 실기에서 5회 중 5회가 안 되면 §13의 대안(양손 벌리기)으로 진입 동작을 바꾼다.

## 시행착오

### T-001 pnpm 11에서 `pnpm test`가 esbuild 빌드 스크립트 때문에 실패 (1단계)

- **증상**: `pnpm install` 뒤 `pnpm test`/`pnpm build`를 치면 `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.2` 와 함께 pnpm 내부 스택이 뜨고 스크립트가 실행되지 않음.
- **원인**: pnpm 10부터 의존성의 postinstall 스크립트를 기본 차단하고, pnpm 11은 스크립트 실행 전 "deps status check"를 돌리며 차단된 빌드가 있으면 실패 처리함. 또 pnpm 11은 `package.json`의 `"pnpm"` 필드를 더 이상 읽지 않는다(`onlyBuiltDependencies`를 거기 넣었더니 무시됨).
- **해결**: 루트의 `pnpm-workspace.yaml`(pnpm이 자동 생성)에 `allowBuilds: { esbuild: true }`를 적음. 팀원도 같은 파일을 쓰므로 `pnpm approve-builds`를 각자 누를 필요 없음.

### T-002 큰 원의 첫 호가 스와이프로 잡힘 (6단계)

- **증상**: "검지로 큰 원을 그리는 동안 스와이프가 발동하지 않는다" 테스트가 실패. 회전 진행 150° 보류 규칙을 넣었는데도 원의 초반(약 84°)에 `swipe_right`가 나옴.
- **원인**: 반지름 1.5 손 크기의 원에서 84° 호의 현 길이는 2×1.5×sin(42°) ≈ 2.0 손 크기, 수직 편차는 r(1−cos 42°) ≈ 0.39 손 크기 → 비율 0.19. 스와이프 조건을 전부 통과한다. 즉 초반 호는 기하학적으로 곡선 스와이프다.
- **해결**: D-010. 손 모양(포인팅 비율)으로 구분. 그리고 나선 테스트 픽스처(0.3→1.5 손 크기)는 중심이 큰 쪽으로 쏠려 반지름 변동계수가 0.35 아래로 내려와 원으로 판정됐다 → 픽스처를 프레임마다 0.4↔1.4로 튀는 궤적으로 바꿈(테스트가 잘못된 경우).

### T-003 손바닥 실행 뒤 쿨다운이 10초 넘게 이어져 스와이프가 전부 무시됨 (1차 실기, 2026-09-08)

- **증상**: 실기 로그 07:30:01~07:30:11. `open_palm` 실행 후 스와이프를 여러 번 했는데 전부 `쿨다운 중`으로 무시됨.
- **원인**: "쿨다운 중 같은 제스처 후보가 계속 보이면 만료를 `t + cooldownMs`로 미룬다"는 규칙(D-008 초안). 스와이프는 손을 편 채로 하므로 손바닥 후보(`open_palm`)가 프레임마다 잡혀 쿨다운이 영원히 연장됐다. 설계 때 "같은 제스처 = 같은 명령을 반복하려는 의도"라고 가정했는데, 실제로는 "다른 제스처를 하는 동안의 손 모양"이었다.
- **해결**: 연장 규칙 삭제. 재실행 방지는 release 규칙(정적 제스처는 포즈를 한 번 풀어야 재무장)만으로 충분하다. 테스트: `open_palm` 실행 후 손을 편 채 1.6초 뒤 `swipe_right`가 실행되어야 함, 같은 포즈가 보여도 `cooldownUntil`이 `실행 시각 + cooldownMs` 그대로여야 함.
- **교훈**: "후보가 보인다"와 "명령을 의도한다"는 다르다. 억제 규칙은 후보가 아니라 실행 이벤트를 기준으로 걸어야 한다.

### T-004 확실한 손바닥·주먹의 포즈 점수가 0.50~0.60에 몰려 대부분 거부됨 (1차 실기)

- **증상**: 개발 패널에서 확실히 편 손도 포즈 점수 0.5x, `minPoseScore`(0.6) 바로 아래라 `신뢰도 부족`.
- **원인**: 점수식이 (1) 손가락별 `0.5 + 0.5·(마진/poseSoftMargin)`의 **최솟값**이었고 (2) `poseSoftMargin`이 0.15였다. 최솟값은 다섯 손가락 중 하나만 경계에 걸려도 전체를 0.5로 끌어내린다. 실제 손은 카메라 각도 때문에 새끼손가락이나 엄지 하나가 자주 경계 근처에 온다. 여기에 soft 0.15는 "마진 0.15(손 크기의 15%)는 돼야 만점"이라는 뜻이라 실제 랜드마크 마진(대개 0.03~0.10)으로는 0.6~0.8이 상한이었다.
- **해결**: (1) 최솟값 → **평균**. 예/아니오 게이트(모든 손가락이 임계값 통과)는 그대로 두었으므로 평균은 "얼마나 확실한가"만 표현한다. 모두 경계면 0.5, 모두 soft 이상이면 1.0, 하나만 경계고 나머지가 확실하면 0.9. (2) `poseSoftMargin` 0.15 → 0.08. 마진 0.04면 0.75, 0.08이면 1.0. (3) 개발 패널에 손가락별 펼침/접힘 마진 원값을 표시해 실기에서 어느 손가락이 발목을 잡는지 보이게 함. 순수 함수 `poseScore(margins, soft)`로 분리해 테스트.
- **되돌릴 조건**: 평균 방식이 "엄지를 반쯤 접은 손"을 손바닥으로 통과시키는 오탐을 만들면 `fingerExtendRatio`/`thumbExtendMargin`(예/아니오 게이트)을 올린다. 점수식은 건드리지 않는다.

### T-005 "왼쪽 스와이프 신뢰도 부족 · 점수 0.82" — 동적 점수가 아니라 손 점수가 원인 (1차 실기)

- **증상**: 동적 판정 점수 0.82인 스와이프가 `신뢰도 부족`으로 거부됨. 로그만 보면 어떤 임계값에 걸렸는지 알 수 없었다.
- **원인**: 상태 머신의 `low_confidence`는 `handScore < minHandScore(0.6)` **또는** `dynamic.score < minDynamicScore(0.5)`인데, 로그에는 동적 점수만 찍혔다. 0.82 ≥ 0.5이므로 실제 원인은 `handScore`. 이 값은 `HandLandmarkerResult.handedness[0][0].score`, 즉 **왼손/오른손 분류 확률**이다. 구조상 항상 0.5 이상이고, 0.5 근처는 "손이 아니다"가 아니라 "손 방향이 애매하다"는 뜻이다. 0.6 하한은 손 신뢰도가 아니라 손 방향 확신도를 요구한 셈이었다. 손 존재 여부는 이미 `minHandDetectionConfidence`/`minHandPresenceConfidence`(vision 옵션, 0.5)가 거른다.
- **해결**: (1) `minHandScore` 기본값 0.6 → 0.5(사실상 통과; 슬라이더로 다시 올릴 수 있음). (2) 무시 로그 상세에 어떤 점수가 어떤 임계값에 미달했는지 기록: `hand 0.55 < 0.60`, `pose 0.30 < 0.60`, `dynamic 0.40 < 0.50`, 복수면 쉼표로 나열. `minDynamicScore`는 이미 config에 있고 0.5(≤0.6)라 그대로 둠.
- **되돌릴 조건**: handedness 대신 진짜 손 신뢰도가 필요하면 `worldLandmarks` 기반 안정성 지표를 따로 만든다. 지금은 없다.

### T-006 "신뢰도 부족"/"쿨다운 중"이 30ms 간격으로 번갈아 찍힘 (1차 실기)

- **증상**: 로그가 프레임마다 쌓여 200건 상한이 몇 초 만에 찼다.
- **원인**: 중복 방지가 "같은 (제스처, 사유)가 연속으로 관측되는 에피소드당 1회"였는데, 점수가 임계값 근처에서 흔들리면 프레임마다 사유가 `low_confidence` ↔ `cooldown`으로 바뀌어 에피소드가 매번 리셋됐다.
- **해결**: 에피소드 규칙에 더해 **시간 스로틀**: 같은 (제스처, 사유)는 `ignoreLogThrottleMs`(500ms) 안에 다시 기록하지 않는다. 상태 머신 안에서 처리하므로 순수 함수 테스트로 고정(30프레임 동안 키당 최대 3건, 간격 ≥ 500ms).

### T-007 주먹 시도 직후 원(타이머)이 실행됨 (2차 실기, 2026-09-08 08:11:15.1, 08:11:21.4)

- **증상**: 주먹을 쥐고 흔들다 놓은 직후 `circle`이 실행되어 타이머가 켜짐.
- **원인**: 원 판정은 검지 끝(8)의 궤적만 봤다. 주먹을 쥔 채 손목이 작은 원을 그리면 검지 끝도 함께 원을 그리므로 회전각·반지름 조건을 통과한다. "원은 검지로 그린다"는 사용 규칙이 스와이프 쪽(D-010)에는 들어가 있었지만 원 쪽에는 없었다.
- **해결**: 원 창 안 프레임의 `circleMinIndexExtendedFraction`(0.8) 이상에서 검지가 펼침 상태여야 원으로 인정. 0으로 두면 게이트가 꺼진다(on/off). 스와이프 보류용 "원 진행 중" 판정에도 같은 게이트를 적용해 주먹이 흔들리는 동안 스와이프까지 막히지 않게 했다. 테스트: 주먹 원 → null, 게이트 0 → circle, 창의 25%만 검지 펼침 → null, 85% → circle.
- **되돌릴 조건**: 사용자가 손을 편 채 원을 그리는 습관이면 그대로 통과한다(검지는 펼쳐져 있음). 검지가 접힌 채 원을 그리는 사용자가 있으면 슬라이더를 0으로.

### T-008 타이머 실행 중 스와이프 도중 원이 오탐됨 (2차 실기)

- **증상**: 스와이프하려고 손을 밀었다 되돌리는 동안 `circle`이 실행돼 타이머가 꺼짐.
- **원인**: 밀었다 되돌리는 손은 갔던 길로 정확히 돌아오지 않고 살짝 위나 아래로 돌아온다. 궤적이 **납작한 고리**가 되어 중심 기준 회전각은 300°를 넘긴다. 반지름 변동계수(0.35)는 긴 축 양끝과 짧은 축 양끝의 차이를 잡기엔 느슨했다(가로 3:세로 1 타원의 변동계수는 약 0.36으로 경계).
- **해결**: 궤적의 x 범위 / y 범위가 `circleMinAspect`(0.6)~`circleMaxAspect`(1.6) 안이어야 원. 스와이프 보류용 "원 진행 중" 판정에는 적용하지 않는다(반원은 본래 2:1). 테스트: 3:1 타원은 반지름 변동 조건을 풀어도 null이고 비율 조건만 끄면 circle(거부 원인이 비율임을 확인), 1:3도 null, 정원은 circle이며 aspect ≈ 1, 1.4:1은 허용.
- **되돌릴 조건**: 카메라를 비스듬히 보면 정원도 원근으로 눌려 보인다. 실기에서 정원이 거부되면 상한을 2.0까지 올린다.

### T-009 주먹 토글 0/3 성공 (2차 실기)

- **증상**: 세 번 시도 모두 실패. 사유는 `유지 시간 부족`, `손이 움직임`, `손 사라짐`.
- **원인**: (1) 2000ms는 주먹을 카메라 앞에서 완전히 정지시키기엔 길다. (2) 유지 중 허용 속도 1.5 손 크기/초는 손바닥 스와이프 오탐 방지용 값인데 주먹에도 같이 적용됐다. 주먹은 스와이프와 겹칠 일이 없다. (3) 주먹은 손가락이 가려져 랜드마크가 자주 튀고 잠깐 사라지는데 유예 150ms는 너무 짧았다.
- **해결**: `fistHoldMs` 2000 → **1200**, `holdGraceMs` 150 → **400**, 유지 중 허용 속도를 포즈별로 분리(`palmHoldMaxSpeed` 1.5 유지, `fistHoldMaxSpeed` 3.0 신설). 테스트: 200ms 관측·300ms 소실을 반복해도 실행됨, 손바닥에는 과한 속도가 주먹에는 허용됨.
- **1200ms 아래로 내리지 않는 이유**: 주먹은 활성화가 꺼진 상태에서도 동작하는 **잠금 해제 경로**다. 조리 중 도구·냄비 손잡이를 쥐는 손은 대개 1초 미만의 주먹이라, 1초 아래로 내리면 사용자가 꺼 둔 모션 단축키가 요리 도중 저절로 켜진다. 1.2초는 "의도적으로 멈춘 주먹"과 "쥐는 동작"을 가르는 하한이며, 30fps 기준 36프레임이라 유예 400ms를 써도 실제 관측 프레임이 충분히 남는다. 더 성공률을 올려야 하면 시간이 아니라 유예·허용 속도를 만진다.
