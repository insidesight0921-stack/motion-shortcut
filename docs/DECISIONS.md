# 기술 결정 기록

형식: **결정 / 대안 / 선택 이유 / 되돌릴 조건**. 시행착오(안 되던 것과 해결법)도 지우지 않고 아래 "시행착오" 절에 남긴다.

## D-001 패키지 버전 고정

- **결정**: react 18.3.1, vite 7.3.6, @vitejs/plugin-react 5.2.0, vitest 4.1.11, typescript ~5.9, zustand 5.0.15, @mediapipe/tasks-vision 1.0.1
- **대안**: react 19.2, vite 8.2(Rolldown), vitest 5.0, typescript 7.0
- **선택 이유**: 기획에서 React 18 확정. Vite 8과 vitest 5는 2026-08~09에 나온 새 메이저라 해커톤 기간에 생태계 이슈를 밟을 위험이 있음. plugin-react 6.x는 peer가 `vite ^8`이라 5.2.0을 사용(peer `^7` 확인). TypeScript 7은 네이티브 포트 신버전이라 제외.
- **되돌릴 조건**: 해커톤 이후 안정화되면 메이저 업데이트. React 19는 기획 결정 변경 시.

## D-002 @mediapipe/tasks-vision 1.0.1과 WASM CDN 버전 고정

- **결정**: 패키지 1.0.1을 쓰고, WASM은 `https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@1.0.1/wasm`으로 **버전을 명시**해 로드. 모델은 Google Storage의 `hand_landmarker.task` float16 v1.
- **대안**: (a) README 예시처럼 버전 미지정 CDN 경로, (b) 0.10.x 마지막 버전, (c) 처음부터 로컬 번들
- **선택 이유**: 1.0.1은 2026-07-31 공개된 정식 릴리스(레지스트리에 보이는 `1.0.1-rc.2026MMDD`는 nightly 태그이며 별개). `vision.d.ts`를 직접 읽어 `FilesetResolver.forVisionTasks`, `HandLandmarker.createFromOptions`, `detectForVideo`, `HandLandmarkerResult.handedness` 시그니처를 확인했고 0.10.x와 동일함. JS 번들과 WASM 버전이 어긋나면 로드 실패가 나므로 CDN 경로에도 같은 버전을 박음. WASM 6개 파일이 npm 패키지에 포함돼 있어서 나중에 `public/`으로 복사하면 로컬 번들 전환이 쉬움(`vision/assets.ts` 상수만 바꾸면 됨).
- **되돌릴 조건**: GPU 델리게이트 초기화 실패 등 런타임 문제가 나오면 먼저 `delegate: 'CPU'`로 전환, 그래도 안 되면 0.10 마지막 버전으로 하향. 오프라인 데모가 필요하면 로컬 번들로 전환.

## D-003 좌표계: 사용자 시점 통일, 거울 변환은 한 곳에서만

- **결정**: `vision/mirror.ts`의 `toUserFrame()`에서 `x → 1 - x`를 한 번 적용. 그 이후 오버레이·판정·테스트는 모두 "사용자 오른쪽 = x 증가 = 화면 오른쪽". 미리보기 `<video>`는 CSS `scaleX(-1)`로 거울 표시. 오버레이 캔버스는 뒤집지 않고 변환된 좌표를 그린다.
- **대안**: (a) 캔버스도 CSS로 뒤집고 원본 좌표를 그림, (b) 판정 함수 안에서 부호만 뒤집음
- **선택 이유**: 반전이 두 군데 이상 있으면 언젠가 두 번 적용되어 좌우가 바뀐다. 변환 지점을 하나로 두고 유닛 테스트에 "x 증가 궤적 → swipe_right"를 고정하는 것이 가장 안전.
- **되돌릴 조건**: 후면 카메라(거울 아님)를 지원하게 되면 `mirror` 플래그를 설정으로 뺀다.

## D-004 엄지 펼침 판정: x축 규칙 대신 손 방향 무관 규칙

- **결정**: 엄지 끝(4)이 새끼 MCP(17)로부터 엄지 IP(3)보다 `thumbExtendMargin`만큼 더 멀면 펼침으로 본다.
- **대안**: 기획 초안의 "엄지는 x축 기준 별도 처리" (엄지 끝 x가 엄지 IP x보다 바깥쪽이면 펼침)
- **선택 이유(비교)**:
  | 항목 | x축 규칙 | 거리 규칙(채택) |
  |---|---|---|
  | 왼손/오른손 | 부호가 뒤집혀 handedness가 필요 | 무관 |
  | 거울 변환 | 변환 여부에 따라 부호 재검토 필요 | 무관 |
  | 손이 기울어짐(회전) | 손이 눕거나 돌아가면 x축 의미가 사라짐 | 손 내부 거리라 회전에 강함 |
  | 직관성 | 단순 | 조금 덜 직관적, 문서 필요 |
  HandLandmarker의 handedness는 "입력이 거울 이미지라는 가정"으로 계산되어 신뢰하기 애매하고, 주먹 판정은 엄지를 제외하므로 이 규칙은 손바닥 판정에만 영향. 실기 튜닝 부담을 줄이는 쪽을 택함.
- **되돌릴 조건**: 실기에서 엄지를 접은 채 나머지를 편 손이 손바닥으로 잡히는 오탐이 잦으면 두 규칙을 AND로 결합하거나 마진을 올린다.

## D-005 스와이프 거리 단위는 손 크기 배수

- **결정**: 스와이프 이동량을 화면 비율이 아니라 "손목–중지MCP 거리(손 크기)"의 배수로 판정한다.
- **대안**: 화면 폭 대비 비율(예: 0.25)
- **선택 이유**: 카메라와의 거리가 달라지면 같은 동작도 화면상 이동량이 달라진다. 손 크기로 나누면 거리에 덜 민감.
- **되돌릴 조건**: 손이 화면 가장자리에 걸려 손 크기 추정이 흔들리면 화면 비율과 혼합.

## D-006 동적 제스처는 정규화 전 좌표로 판정

- **결정**: `TrajectoryBuffer`에는 사용자 시점 프레임의 원본(0~1) 좌표와 손 크기를 저장하고, 스와이프·원은 이 좌표로 판정한다. 정규화 좌표는 정적 포즈에만 쓴다.
- **선택 이유**: 손목 기준 정규화는 평행이동을 제거하므로 손 전체가 움직이는 스와이프는 정규화 좌표에서 보이지 않는다(시행착오 예방 차원에서 기록).

## D-007 활성화 단축키 Ctrl+Shift+M

- **결정**: 모든 플랫폼에서 `Ctrl+Shift+M` (macOS도 Cmd가 아닌 Ctrl).
- **대안**: Cmd+Shift+M, Space
- **선택 이유**: Cmd+Shift+M은 Chrome 프로필 메뉴에 이미 묶여 있음. Space는 YouTube iframe이나 버튼 포커스와 충돌.
- **되돌릴 조건**: 팀원 환경에서 충돌 보고 시 `ui/shortcuts.ts` 상수 변경.

## D-008 상태 머신 세부 규칙

- **결정**: `executing → cooldown` 전이에서 `TrajectoryBuffer.clear()`를 호출한다. 정적 제스처는 실행 후 포즈를 한 번 놓아야(release) 재무장된다. 쿨다운 중 같은 제스처 후보가 계속 보이면 쿨다운 만료 시각을 계속 뒤로 미룬다. 원 판정의 누적 회전각은 **부호 있는 합**으로 계산해 왕복(좌우로 흔들기)이 원으로 잡히지 않게 한다.
- **선택 이유**: 실행 직후 버퍼에 남은 궤적이 다음 틱에서 같은 제스처로 재검출되는 것을 막는다. 손바닥을 계속 들고 있는 동안 재생/일시정지가 반복되는 것을 막는다. 부호 없는 합은 지그재그도 300°를 넘긴다.
- **되돌릴 조건**: 없음(테스트로 고정).

## 시행착오

### T-001 pnpm 11에서 `pnpm test`가 esbuild 빌드 스크립트 때문에 실패 (1단계)

- **증상**: `pnpm install` 뒤 `pnpm test`/`pnpm build`를 치면 `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.2` 와 함께 pnpm 내부 스택이 뜨고 스크립트가 실행되지 않음.
- **원인**: pnpm 10부터 의존성의 postinstall 스크립트를 기본 차단하고, pnpm 11은 스크립트 실행 전 "deps status check"를 돌리며 차단된 빌드가 있으면 실패 처리함. 또 pnpm 11은 `package.json`의 `"pnpm"` 필드를 더 이상 읽지 않는다(`onlyBuiltDependencies`를 거기 넣었더니 무시됨).
- **해결**: 루트의 `pnpm-workspace.yaml`(pnpm이 자동 생성)에 `allowBuilds: { esbuild: true }`를 적음. 팀원도 같은 파일을 쓰므로 `pnpm approve-builds`를 각자 누를 필요 없음.
